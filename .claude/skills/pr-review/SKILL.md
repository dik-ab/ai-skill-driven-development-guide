# PR レビュー手順

このファイルは起動時には読み込まれない。上の frontmatter（name + description）だけが
「利用可能な skill 一覧」としてセッションに常駐し、レビュー依頼が来たときに初めて本文が展開される。

## Step 1: 対象の確定

1. レビュー対象を確定する: PR 番号なら `gh pr diff <N>`、指定が無ければ `git diff origin/main`。
2. 変更ファイルから対象領域（frontend / backend）を判定し、**該当する `.claude/rules/*.md` を読む**。
   レビュー基準はこの skill ではなく rules と設計書が持つ。skill が持つのは手順だけ。

## Step 2: 観点別レビュー（1 サブエージェント 1 観点）

以下の観点ごとに**独立したサブエージェント**を起動する。全部盛りの 1 エージェントにしない
（観点を混ぜると全部が浅くなる）。各エージェントには **diff と仕様だけ**を渡し、
実装時の会話や意図の説明は渡さない（作者バイアスの排除）。

| 観点 | ミッション（命令形で渡す） |
|---|---|
| SPEC | 要求を満たしているか。**頼まれていない変更が混ざっていないか** |
| REGRESSION | このコードが壊れる具体的シナリオを最低 3 つ挙げよ。既存挙動・API 契約への影響 |
| TEST | テスト自体を疑え。弱いアサーション、通すためのハック、スキップ・期待値の書き換え |
| SECURITY | 入力検証、認可、シークレット混入（変更が認証・入力処理・外部 I/O を含む場合のみ） |

- 「問題ないか確認して」という聞き方をしない。LGTM に寄る。
- **指摘ゼロなら正直にゼロと報告させる。** 無理に指摘を捏造させない。

## Step 3: 裏取りと報告

1. 挙がった指摘は、別の検証エージェント（または自分で再現確認）で裏取りしてから採用する。
   false positive を人間に渡さない。
2. 深刻度（critical / major / minor）でランク付けし、critical から報告する。
3. 報告には必ず「確認したが問題なしだった観点」も明記する。何を見ていないかが分かるように。
