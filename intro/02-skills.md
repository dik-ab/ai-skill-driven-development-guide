# 02. 前提 1: 入口・ルール・スキルの 3 層

この章で分かること:

- AI に読ませるファイルは 3 種類しかないこと
- 3 種類は「読まれるタイミング」が違うこと
- スキルは「説明文だけが常駐し、本文は呼ばれたときに読まれる」こと

## 3 層の表

これが入門編で一番大事な 1 枚です。

| 層 | ファイル | いつ読まれるか | だから |
|---|---|---|---|
| 常駐 | `CLAUDE.md` 全文 と 各スキルの説明文だけ | セッション開始時、毎回 | 一等地。薄く保つ |
| 条件付き | `.claude/rules/*.md` | 対象パスのファイルを触るとき | 領域外のルールを混ぜない |
| 呼び出し | `.claude/skills/*/SKILL.md` の本文、仕様書 | スキルが選ばれたとき | 重い手順はここへ逃がす |

図書館で言えば「目次だけ常駐、本文は貸出式」です。
全ルールを入口に書くと、誤字修正のセッションでもレビュー観点の一覧を読ませることになり、本当に守ってほしい行が埋もれます。

## 層 1: 入口 `CLAUDE.md`

AI が作業を始めるとき、必ず最初に読むファイルです。書くのは次の 4 つだけです。

```markdown
# 会議室予約アプリ エージェントガイド

## リポジトリの地図
- Web 画面: `apps/web`
- API サーバー: `apps/api`
- API 契約: `openapi.yaml`
- 仕様書（正本）: `../meeting-room-specs/`

## 作業順序
1. 変更対象を Web / API / 文書に分類する。
2. 対象に合う `.claude/rules/*.md` を読む。
3. 仕様書を読んでから設計判断をする。
4. 変更は最小にし、対象範囲の検証を実行する。
5. 未解決事項と失敗した検証は隠さず報告する。

## 必ず守ること
- 生成されたクライアントコードは手で直さない。
- 仕様通りに作れないときは、黙って別案にせず止まって聞く。
- レビュー結果を「問題なさそう」で終えない。

## 代表コマンド
- Web テスト: `pnpm --filter web test`
- API テスト: `./gradlew :apps:api:test`
```

入口が答えるのは「どの領域か」「最初にどこを見るか」「何を禁止するか」「代表コマンドは何か」です。
「どう実装するか」は書きません。それはスキルの仕事です。

## 層 2: ルール `.claude/rules/`

領域ごとに「常に守る制約」を置きます。手順ではなく制約です。

```markdown
---
paths:
  - apps/api/**
---
# API サーバーのルール

- 業務ロジックはドメイン層に置く。Controller に書かない。
- DB を変更するときは必ずマイグレーションファイルを作る。
- 例外はそのまま投げず、共通のエラー形式に変換する。
```

先頭の `paths` が「このルールは `apps/api` 配下を触るときだけ有効」という条件です。
Web 画面の作業中に API のルールが混ざることを防ぎます。

## 層 3: スキル `.claude/skills/`

「この種類の作業はこう進める」という手順書です。1 スキル 1 フォルダで、`SKILL.md` が必須です。

```markdown
---
name: pr-review
description: >
  PR やブランチの変更をレビューする。
  「レビューして」「マージ前に確認」「コードチェック」で使う。
  実装作業そのものには使わない（feature-dev を使う）。
---

# PR レビュー手順

## 手順 1: 対象を確定する
差分を取得し、変更ファイルから領域を判定して該当ルールを読む。

## 手順 2: 観点ごとに別のサブエージェントで見る
仕様適合、既存機能への影響、テストの妥当性、セキュリティ。

## 手順 3: 裏取りして報告する
指摘は再現確認してから採用する。深刻度順に報告する。指摘ゼロなら「ゼロ」と書く。
```

先頭の `---` で囲まれた部分が「説明文」です。ここだけが常駐します。
ユーザーが「レビューして」と言ったとき、AI は説明文と依頼を照合して `pr-review` を選び、そこで初めて本文を読みます。

説明文の書き方が、スキルの起動精度をほぼ決めます。

- 何をするスキルか
- ユーザーが実際に使う言い回し（日本語も英語も）
- 使わない場面と、代わりに使うスキル

## ルールとスキルの違い

初学者が一番混乱する点です。

| | ルール | スキル |
|---|---|---|
| 答える質問 | 常に何を守るか | この作業をどう進めるか |
| 選ばれる条件 | 触っているファイルのパス | 依頼の意味 |
| 例 | 「生成コードを手で直さない」 | 「レビューは観点を分けて見る」 |

原則は 2 つです。「何を守るかはルール、どう進めるかはスキル」「下の層に置けるものを上に置かない」。

## 一連の流れ

```text
「この PR をレビューして」
  ① 常駐している説明文と照合 → pr-review が選ばれる
  ② SKILL.md 本文がここで初めて読まれる
  ③ 差分が API 側なら、rules/api.md がここで読まれる
  ④ 手順に従い、観点別にサブエージェントを起動
  ⑤ 裏取りして深刻度順に報告
```

観点分割も裏取りも、毎回人が指示したのではありません。スキルに一度書いたから毎回起こります。
「人の修正が永続ルールになる」の最小実装がこれです。
