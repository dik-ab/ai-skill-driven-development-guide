# 12. 実践 1: 既存コードのリファクタに AI 駆動開発をどう使うか

この章で分かること:

- リファクタが新機能追加より難しい理由と、AI 駆動開発のどこが効くか
- 進める順番。特性テストを AI に書かせてから構造を変える
- レビュースキルがリファクタで何を見るか
- 手動テストをどこまで使い、どこから自動に寄せるか

## 状況

フロントとバックエンドの 2 つのリポジトリがあり、それぞれ別の機能ブランチで並行作業が進んでいます。その中の、責務が膨らんだファイルを整理したい。仕様書は「何を作るか」は書いてあるが、「今このファイルがどう動いているか」までは書いていない。よくある状況です。

## リファクタは何が難しいか

リファクタは「振る舞いを変えずに構造を変える」作業です。難しさは 1 点に集約されます。**「振る舞いが変わっていない」ことを、どう証明するか**です。

新機能追加なら、仕様書が「こう動くべき」を持っています。AI はそれを読んで実装し、テスト契約で照合できました（05 章）。リファクタでは、こう動くべきの正本が仕様書ではなく**今のコード**にあります。01 章で「既存コードは正本ではない」と言いましたが、リファクタでは例外的に、既存コードの振る舞いが守るべき対象になります。

だから AI 駆動開発の道具のうち、リファクタで主役になるのは次の 3 つです。

| 道具 | 新機能での役割 | リファクタでの役割 |
|---|---|---|
| テスト契約（05 章） | 仕様書から「こう動くべき」を固定する | 今のコードから「こう動いている」を固定する（特性テスト） |
| レビュースキル（04 章） | 仕様を満たしているか | 振る舞いが変わっていないか。頼まれていない変更が混ざっていないか |
| フック（10 章） | 生成物・危険操作を止める | 同じ。リファクタは触るファイルが多いので、むしろ効く |

## 進める順番

### 0. 作業を分離する

並行している機能ブランチにリファクタを混ぜません。混ぜると、レビューで「この差分は機能なのか整理なのか」が判別できなくなり、REGRESSION の観点が効かなくなります。

- リファクタ用のブランチ（可能なら worktree）を最新の main から切る
- 機能ブランチ側で同じファイルを触っている場合は、どちらを先にマージするか先に決める
- 1 PR に 1 種類の変更だけ入れる。名前変更、抽出、移動を別 PR にする

### 1. 現状を言葉にさせる（05 章のフェーズ 1 に相当）

AI に対象ファイルを読ませ、「このファイルは今、何をしているか」を箇条書きにさせます。

```text
「このファイルの責務、外から呼ばれている関数、呼んでいる先、副作用（DB、API、ストレージ、ログ）を洗い出して。
  推測は入れず、コードから読み取れることだけ。分からない箇所は『不明』と書いて」
```

出てきた一覧を人が読み、「これは仕様通り」「これはバグだが今は触らない」「これは死んでいるコード」に分類します。この一覧が、この作業での正本の代わりです。仕様書があれば照合し、食い違いは記録だけして直しません。

### 2. 特性テストを AI に書かせる（フェーズ 3 に相当）

特性テスト（characterization test）は、**正しい振る舞いではなく、今の振る舞い**をそのまま固定するテストです。手順 1 の一覧の各行を、入力と出力の形にします。

```text
「手順 1 の一覧の各項目について、今のコードの振る舞いをそのまま固定するテストを書いて。
  期待値は仕様書ではなく、実際に今のコードを動かした結果にする。
  境界値と異常系も、今どう動くかをそのまま記録する。
  バグと思われる挙動も、直さずに『現状』としてテストに残し、コメントで印を付けて」
```

ここが新機能と一番違う点です。バグを見つけても直しません。直すのは別 PR です。リファクタの PR で振る舞いが変わると、レビューで「意図した変更か、壊したのか」が判別できなくなります。

特性テストは green になるまで AI に直させます。テストが失敗するなら、手順 1 の読み取りが間違っています。

### 3. 小さく刻んで構造を変える（フェーズ 4 に相当）

特性テストが green の状態から、1 つずつ変えます。

```text
変更前: green
  ↓ 関数を抽出
green を確認
  ↓ 名前を変える
green を確認
  ↓ 別ファイルへ移す
green を確認
```

red になったら、その 1 手を戻します。AI に「なぜ red になったか」を説明させ、振る舞いの変更が必要なら手順 1 に戻って一覧を更新します。

この間、フック（10 章）が生成物への編集や危険なコマンドを止めています。触るファイルが多いリファクタで、AI が「ついでに」生成物を直そうとするのを機械的に防げます。

### 4. 検証（フェーズ 5 に相当）

対象テスト、lint、型チェック、ビルド。画面に影響があれば実ブラウザ確認（13 章）。特性テストは全部 green のはずです。1 つでも red なら、それは「振る舞いが変わった」ことの証拠です。

### 5. レビュー

レビュースキル（04 章）の 4 観点は、リファクタでは次のように読み替わります。

| 観点 | 新機能のとき | リファクタのとき |
|---|---|---|
| 仕様適合 | 要求を満たしているか | **頼まれていない振る舞いの変更が混ざっていないか**。「ついでの修正」を見つける |
| 既存機能への影響 | 壊れる状況を 3 つ挙げよ | **主役**。呼び出し元、境界値、副作用の順序が変わっていないか |
| テストの妥当性 | 弱い検証、通すための細工 | **特性テストが通すために期待値を書き換えられていないか**。手順 2 で固定した値と PR の値が一致するか |
| セキュリティ | 入力検証、認可、秘密情報 | 認可チェックの位置が移動で抜けていないか |

レビューには差分と手順 1 の一覧を渡します。実装時の会話は渡しません（04 章）。

### 6. 手動テストは「自動で証明できないもの」だけ

手動テストで進めたい、という考えは半分正しいです。手動をゼロにはできません。ただ、**先に特性テストを書かせてから**にします。理由は 3 つです。

1. **2 回目以降に再実行できる**。リファクタは 1 回で終わりません。手動テストは次の PR でもう一度人がやることになります
2. **レビューの根拠になる**。「手で見て大丈夫でした」は第三者が検証できません。green のテスト一覧は検証できます
3. **AI 自身が壊したことに気づける**。手順 3 で red になれば AI はその場で戻せます。手動だと、壊れたことに気づくのは人が見たときです

そのうえで、手動は自動化できないものに限定します。何が自動化できていないかは、13 章の形で書き出します。AI に「変更した箇所から影響する画面と操作を列挙して、手動確認のチェックリストを作って」と頼めば、人が見るべき箇所の一覧が出ます。

## 重さの決め方

05 章の「すべてに同じ重さを使わない」はリファクタにも当てはまります。

| リスク | 例 | 進め方 |
|---|---|---|
| 低 | 名前変更、整形、コメント | 既存テスト + lint + 型チェック。特性テストは不要 |
| 中 | 関数の抽出、責務の分割、ファイル移動 | 手順 1〜5。特性テストを書く |
| 高 | 公開 API の形、DB スキーマ、認可の位置、複数リポジトリにまたがる | 05 章の AIDLC 完全版。質問ファイルと人の承認 |

フロントとバックエンドの両方に手が入るなら「高」です。API の契約（OpenAPI）を先に固定し、両側の特性テストがその契約を参照する形にします。

## 実例: エージェント基盤を「A2A 対応」に向けてリファクタする

架空ではない実例です。AWS 上に「監督エージェントがサブエージェントを呼ぶ」構成を持つプロジェクトで、AI にリポジトリを読ませて「エージェント間連携（A2A）の観点で評価して」と頼みました。返ってきた評価と、そこからどう進めるかを、この章の手順に当てて示します。

### AI の評価（要約）

結論は「A2A はまだ実現できていない。マルチエージェントの土台はあるが、A2A へ進む足場としては弱い」でした。根拠は 4 点です。

| 指摘 | 中身 | 何が問題か |
|---|---|---|
| A2A と呼べない | 動いているのは AWS 閉域の Multi-Agent Collaboration。Agent Card も JSON-RPC の受け口も無く、外部エージェントと繋がる口が無い（grep で該当ゼロ） | 「A2A 対応」という言葉と実装が一致していない |
| 接続がコードになっていない | 監督とサブエージェントの接続設定はコンソールで手動。Terraform 側は `ignore_changes` で無視、エイリアス作成も手動 | エージェントを増やすたびに再現性が崩れる。誰も正確な構成を知らない状態 |
| 契約が無い | 監督とサブエージェントの入出力は自然言語の instruction 任せ。スキーマ無し。応答のパース処理は「確定次第」と TODO のまま | 振る舞いを固定できない。テストが書けない |
| 活きる資産はある | WebSocket のメッセージ仕様（共通エンベロープ、correlationId、inReplyTo、ack/answer/directive/error の型）と、監査テーブル・構造化ログ | A2A の Task と Message の考え方に近い。ここは捨てない |

AI が提案した優先順は、接続設定のコード化 → 入出力スキーマの固定 → エージェントを独立したサービスに切り出す → 外部公開なら Agent Card と認証、でした。

### この評価の何が良かったか

- **grep の結果を根拠にしている**。「a2a、agent card、mcp でゼロ件」は第三者が再現できます。04 章の「正本の根拠」と同じです
- **言葉と実装のズレを指摘している**。「A2A」という名前が付いているが中身は別物、という指摘は、人が気づきにくい種類のものです
- **捨てるものと活かすものを分けている**。全部作り直せ、ではなく、メッセージ仕様と追跡基盤は再利用できると言っています
- **公式の仕組みを名指ししている**。Terraform の `aws_bedrockagent_agent_collaborator`、A2A サーバーをホストできる AgentCore Runtime、Agent Card の配置場所。次の一手が具体的です

### この章の手順に当てる

このリファクタは「高」リスクです。公開契約（エージェント間の入出力）を決め、インフラの管理方法を変え、複数のコンポーネントにまたがります。05 章の AIDLC 完全版で進めます。

**手順 0: 分離する**。「接続設定のコード化」「入出力スキーマの固定」「サービスとしての切り出し」は別 PR です。特に 1 つ目はインフラだけ、2 つ目はアプリだけで完結するので、混ぜる理由がありません。

**手順 1: 現状を言葉にする**。AI の評価がすでにこれです。ただし「コンソールで手動設定されている現在の接続内容」は、コードに無いのでコンソールから読み取って文書にします。これが無いとコード化した結果が正しいか判断できません。

**手順 2: 特性テストを書く**。ここで問題が出ます。入出力が自然言語任せなので、今の振る舞いを固定するテストが書けません。だからこのリファクタでは、**スキーマの固定が特性テストの前提**になります。順番はこうです。

```text
1. 監督 → サブエージェントへ渡している内容を、実際のログから 10〜20 件集める
2. 共通する形を JSON スキーマとして書き起こす（AI に起票させ、人が確認する）
3. そのスキーマに対する入出力テストを書く。これが特性テスト
4. worker 側のパース処理の TODO を、スキーマに合わせて潰す
```

ADR を 1 枚書くタイミングです。「なぜ自然言語の instruction ではなくスキーマにするのか」「なぜ AWS 閉域の仕組みから A2A に向けるのか」は、後から戻すコストが高い判断です。

**手順 3: 小さく刻む**。接続設定のコード化は、Terraform の `import` で既存の設定を取り込み、`plan` が差分ゼロになることを確認してから `ignore_changes` を外します。この「差分ゼロ」が、インフラにおける green です。10 章のフックが `terraform apply` を止めるので、`plan` までは AI が回し、`apply` は人がやります。

**手順 4: 検証**。スキーマに対するテスト、Terraform の `plan` 差分ゼロ、既存の WebSocket メッセージ仕様のテスト。correlationId で追跡できる構造化ログがすでにあるので、変更前後で同じリクエストを流し、ログの形が変わっていないことを比較できます。

**手順 5: レビュー**。観点は表の通りです。特に「既存機能への影響」で、活かす資産（メッセージ仕様、監査テーブル）が壊れていないかを見ます。

**手順 6: 手動**。エージェントの応答品質は機械で判定しきれません。13 章の型で「証明していないこと」に「応答の意味的な正しさ」を書き、代表的なシナリオを人が確認します。

### この実例で分かること

「A2A 対応にしたい」という 1 行の依頼に対して、AI 駆動開発の道具がそれぞれ何をしたか。

- **レビュースキル（04 章）**が、言葉と実装のズレを grep の根拠付きで見つけた
- **正本の考え方（03 章）**が、「接続設定が Terraform ではなくコンソールにある」を「正本が無い」と言い換えさせた
- **テスト契約（05 章）**が、「スキーマが無いとテストが書けない」を見つけ、作業順を決めた
- **フック（10 章）**が、Terraform の `apply` を人に残した
- **ADR**が、なぜ閉域の仕組みから離れるのかを残す場所になった

道具は新機能追加のときと同じです。違うのは、正本が「今のコード」であり、その今のコードすら一部はコンソールにしか無かった、という点でした。

## この章で AI 駆動開発が生きている箇所

- **判断を先に外に出す**。手順 1 の一覧と手順 2 の特性テストが、構造を変える前に「守るもの」を固定した
- **完了条件が AI の外にある**。特性テストが green かどうかで、AI の「できました」に頼らない
- **別の目で見る**。レビュースキルが、実装した AI とは別のコンテキストで「振る舞いが変わっていないか」だけを見る
- **機械で止める**。フックが、触るファイルが多い作業での事故を防ぐ
- **手動は残るが、範囲が決まる**。何を人が見るかが一覧になっている

新機能追加とリファクタで道具は同じです。違うのは、正本が仕様書か今のコードか、という 1 点だけです。
