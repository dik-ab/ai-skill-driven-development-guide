# 11. まとめ: 実装依頼からマージまでの全体フローと、なぜ「問題ない」と言えるのか

この章で分かること:

- 「機能を追加して」と頼んだ瞬間からマージまでに、何がどの順で読まれ、どのスキルが動くか
- 各段階が、01 章で挙げた「AI がズレる 5 つの型」のどれを止めているか
- 最後に「問題ない」と言うとき、その根拠が何で、何が残っているか

## 依頼

```text
「会議室予約にキャンセル機能を追加して」
```

この 1 行から始めます。使うのは、この repo のルートに置いてある実物です。

```text
CLAUDE.md
.claude/rules/        frontend.md  backend.md
.claude/skills/       feature-dev  pr-review  browser-test  (aws-readonly  drawio-diagram)
.claude/hooks/        block-generated-edit.sh  block-dangerous-commands.sh
../sample-specs/      仕様書（正本。このデモでは架空）
```

## 全体フロー

```text
 時点            読まれる・動くもの                          決めた人
─────────────────────────────────────────────────────────────────────
 ① セッション開始  CLAUDE.md 全文、各スキルの説明文だけ          リポジトリ管理者
 ② 依頼           feature-dev の説明文と一致 → 選択            スキル作者
                  (pr-review は「実装には使わない」で除外)
 ③ 手順 1         feature-dev 本文 → rules/backend.md          スキル作者、領域担当
                  → 仕様書（業務ルール、API 契約、画面）         仕様の所有者
 ④ 矛盾の確認     仕様書で解決できない点だけ質問ファイルに        AI が起票、人が回答
 ⑤ テスト先行     契約をテストコードに。境界値・異常系を確定       AI が提案、人が確認
 ⑥ 実装           編集ごとにフックが判定。生成物・危険操作は拒否   フック作者
 ⑦ 検証           対象テスト、lint、型チェック                     CLAUDE.md の代表コマンド
                  画面があれば browser-test で実ブラウザ確認      スキル作者
 ⑧ 自己チェック   「頼まれていないことをしていないか」            feature-dev の完了条件
 ⑨ PR             差分、検証結果、未解決事項を本文に               PR テンプレート
 ⑩ レビュー       pr-review: 観点別サブエージェント → 裏取り       スキル作者
 ⑪ ゲート         CI で lint / test / build / 生成物差分           CI 設定
 ⑫ 承認・マージ   指摘と残リスクを見て人が判断                    人
```

右列に注目してください。AI がその場で決めたものは 1 つもありません。すべて事前にファイルとして置かれた判断です。AI がやったのは、置かれた手順を順に実行することです。

## 各時点で何が起きているか

### ① と ②: 入口と選択

セッション開始時に常駐するのは `CLAUDE.md` の全文と、各スキルの説明文だけです。「機能追加して」が feature-dev の説明文にある「機能追加して」「実装して」と一致し、選ばれます。pr-review の説明文には「実装作業そのものには使わない」とあるので候補から外れます。

ここで初めて feature-dev の本文が読まれます。02 章の「目次だけ常駐、本文は貸出式」です。

### ③: 読む順番が手順になっている

feature-dev の手順 1 は「該当ルールを読む → 正本を読む → 設計書で答えが出る質問をユーザーに投げない」です。変更対象が `apps/api` なので `rules/backend.md` が有効になり、続いて業務ルールの BR-01〜03 と API 契約を読みます。

「読むべきものを読まない」というズレは、ここで止まります。読む順番が手順に書かれているからです。

### ④: 質問は仕様書で解決できないものだけ

BR-01〜03 で「誰が」「いつまで」は決まります。書いていない「繰り返し予約の扱い」だけが質問ファイルになります。06 章で見た通り、人は回答欄に 1 文字書くだけです。

「仕様を推測で埋める」というズレは、ここで止まります。

### ⑤: 完了条件が先に決まる

テストを先に書きます。「開始 30 分前ちょうど」「権限なし」「二重送信」など、境界値と異常系がこの時点で確定します。

「終わったと思い込む」というズレは、ここで止まります。完了条件が AI の外に、テストとして置かれたからです。

### ⑥: 編集のたびにフックが見ている

実装中、AI が `generated/` を触ろうとすれば拒否され、`git push --force` を打とうとすれば拒否されます。AI がルールを忘れていても止まります。

「既存コードを正解扱いして生成物を直す」「取り返しのつかない操作」は、ここで止まります。

### ⑦ と ⑧: 検証と自己チェック

対象テスト、lint、型チェックを実行し、結果を成功も失敗もそのまま報告します。画面があれば browser-test で「テストが通った」と「画面で動く」を分けて確認します。最後に「頼まれていないことをしていないか」を自己チェックします。

「品質を過信する」というズレは、ここで止まります。実行するコマンドが決まっていて、報告の形が決まっているからです。

### ⑨ から ⑪: 別の目で見る

PR には検証結果と未解決事項が書かれます。pr-review が動き、観点別のサブエージェントに差分と仕様だけを渡します。作者の意図は渡しません。挙がった指摘は裏取りしてから採用し、指摘ゼロの観点は「ゼロ」と明記します。CI が lint、テスト、ビルド、生成物の差分を機械的に見ます。

「小さなズレが積み重なる」は、ここで止まります。実装した AI とは別のコンテキストが、仕様と差分だけを見るからです。

### ⑫: 人が決める

残った指摘と残リスクを見て、人がマージを判断します。ゲートを例外的に外すなら、その責任も人が持ちます。

## なぜ「問題ない」と言えるのか

「AI がテストを書いて通ったから」ではありません。層が重なっているからです。

| 層 | 何を保証するか | 01 章のズレのどれを止めるか |
|---|---|---|
| 正本 | 何を作るべきかが AI の外に定義されている | 仕様を推測する |
| 読む順番（スキル） | 正本を読んでから判断する | 読むべきものを読まない |
| テスト契約 | 完了条件が実装前に固定されている | 終わったと思い込む |
| フック・権限 | 禁止操作が機械的に止まる | 既存コードを正解扱い、破壊的操作 |
| 品質ゲート | lint、テスト、ビルドを機械が判定する | 品質を過信する |
| 独立レビュー | 別コンテキストが仕様と差分だけを見る | 小さなズレの蓄積 |
| 人の承認 | 例外判断と最終責任 | すべての残余 |

どの層も単独では穴があります。注意書きは読み飛ばされ、フックは外せ、テストは書いた条件しか見ず、レビューは見落とします。重ねることで、1 つの穴がそのまま本番に届く確率を下げています。

## それでも残るもの

正直に書きます。次は上の層では止まりません。

- **仕様書そのものが間違っている**。AI は正本に忠実に作るので、正本が誤っていれば誤りを忠実に実装します。防ぐのは仕様書側のレビューです（本編 08 章）
- **テストに書かれていない業務ルール**。テスト契約に漏れた条件は検証されません。防ぐのは業務ルールに ID を付けてテストと対応させる運用です
- **フックのすり抜け**。フックはクライアント依存です。CI と権限で二重化します
- **レビューの見落とし**。AI も人も見落とします。だから「何を見て何を見ていないか」を報告に残します

失敗が起きたら `tasks/lessons.md` に書き、2 回目はルールかスキルかフックに昇格させます（07 章）。層は最初から完成しているのではなく、失敗のたびに厚くなります。

## 「問題ない」の正しい言い方

完了報告は「できました」ではなく、次の形になります。

```markdown
## 変更内容
- Reservation.cancel() と CancelReservationUseCase を追加

## 検証
- [x] ./gradlew :apps:api:test （成功）
- [x] pnpm --filter web test / typecheck / build （成功）
- [x] SCR-010 でキャンセル操作を実ブラウザ確認
- [ ] 未実行: 負荷試験（対象外）

## レビュー
- 仕様適合: 指摘なし
- 既存機能への影響: 指摘 1 件（修正済み）
- テスト: 指摘なし
- セキュリティ: 対象外（認可ロジック変更なし）

## 未解決事項
- 繰り返し予約の全回キャンセルは別 issue

## 正本との差分
- Reservation.status に CANCELLED を追加。仕様書へ追記済み
```

「問題ない」とは「問題がゼロ」ではなく、「どこまで見て、何が残っているかを説明できる」状態のことです。それを AI に毎回言わせる仕組みが、この入門編で説明してきた全部です。

## 締め

AI に任せられる範囲は、AI の賢さで決まるのではありません。正本、テスト、フック、ゲート、レビューを設計した範囲に比例して広がります。設計した範囲の外は、今日も人がやります。だからエンジニアの仕事は消えず、この設計へ移動します。

明日からやる 1 つは 07 章に戻ってください。`CLAUDE.md` 1 枚と、レビューのスキル 1 枚です。
