# 11. まとめ: 実装依頼からマージまでの全体フローと、なぜ「問題ない」と言えるのか

この章で分かること:

- 「機能を追加して」と頼んだ瞬間からマージまでに、何がどの順で読まれ、どのスキルが動くか
- 各段階が、01 章で挙げた「AI がズレる 5 つの型」のどれを止めているか
- 最後に「問題ない」と言うとき、その根拠が何で、何が残っているか

## 依頼

```text
「会議室予約にキャンセル機能を追加して」
```

この 1 行から始めます。使うのは、この repo のルートに置いてある実物です。

```text
CLAUDE.md
.claude/rules/        frontend.md  backend.md
.claude/skills/       feature-dev  pr-review  browser-test  (aws-readonly  drawio-diagram)
.claude/hooks/        block-generated-edit.sh  block-dangerous-commands.sh
../sample-specs/      仕様書（正本。このデモでは架空）
```

## 全体フロー

```text
 時点            読まれる・動くもの                          決めた人
─────────────────────────────────────────────────────────────────────
 ① セッション開始  CLAUDE.md 全文、各スキルの説明文だけ          リポジトリ管理者
 ② 依頼           feature-dev の説明文と一致 → 選択            スキル作者
                  (pr-review は「実装には使わない」で除外)
 ③ 手順 1         feature-dev 本文 → 仕様書（業務ルール、       スキル作者
                  API 契約、画面）→ 変更対象を判断               仕様の所有者
                  → 触るパスに合う rules（backend.md、frontend.md） 領域担当
 ④ 矛盾の確認     仕様書で解決できない点だけ質問ファイルに        AI が起票、人が回答
 ⑤ テスト先行     契約をテストコードに。境界値・異常系を確定       AI が提案、人が確認
 ⑥ 実装           編集ごとにフックが判定。生成物・危険操作は拒否   フック作者
 ⑦ 検証           対象テスト、lint、型チェック                     CLAUDE.md の代表コマンド
                  画面があれば browser-test で実ブラウザ確認      スキル作者
 ⑧ 自己チェック   「頼まれていないことをしていないか」            feature-dev の完了条件
 ⑨ PR             差分、検証結果、未解決事項を本文に               PR テンプレート
 ⑩ レビュー       pr-review: 観点別サブエージェント → 裏取り       スキル作者
 ⑪ ゲート         CI で lint / test / build / 生成物差分           CI 設定
 ⑫ 承認・マージ   指摘と残リスクを見て人が判断                    人
```

右列に注目してください。AI がその場で決めたものは 1 つもありません。すべて事前にファイルとして置かれた判断です。AI がやったのは、置かれた手順を順に実行することです。

## 各時点で何が起きているか

### ① と ②: 入口と選択

セッション開始時に常駐するのは `CLAUDE.md` の全文と、各スキルの説明文だけです。「機能追加して」が feature-dev の説明文にある「機能追加して」「実装して」と一致し、選ばれます。pr-review の説明文には「実装作業そのものには使わない」とあるので候補から外れます。

ここで初めて feature-dev の本文が読まれます。02 章の「目次だけ常駐、本文は貸出式」です。

### ③: なぜ rules が読まれるのか（ここが一番分かりにくい）

feature-dev の手順 1 は「該当するルールを読む → 正本を読む → 設計書で答えが出る質問をユーザーに投げない」です。ここで初学者がつまずく疑問を 3 つ、順に解きます。

**疑問 1: なぜ `rules/backend.md` が読まれるのか。`CLAUDE.md` に「rules を読め」と書いてあるからか**

半分正しいです。読まれる経路は 2 つあります。

| 経路 | 仕組み | 誰が用意したか |
|---|---|---|
| 自動 | Claude Code が `.claude/rules/*.md` を自分で見つける。先頭の `paths` に書かれたパスのファイルを AI が読んだり編集したりした時点で、そのルールが読み込まれる | クライアント（Claude Code）の機能 |
| 指示 | `CLAUDE.md` の作業順序と feature-dev の手順 1 に「対象に合うルールを読む」と書いてある | リポジトリ管理者、スキル作者 |

`rules/backend.md` の先頭はこうなっています。

```yaml
---
paths:
  - "apps/backend/**"
---
```

これは「`apps/backend/` 配下のファイルを触るときだけ、このルールを有効にする」という条件です。AI が `apps/backend/src/.../Reservation.java` を開いた瞬間に、クライアントが自動でこのルールを読み込みます。`CLAUDE.md` に書いてあるから読まれるのではなく、**触ったパスが一致したから**読まれます。

では、なぜ `CLAUDE.md` やスキルにも「読め」と書くのか。02 章と同じ理由です。自動読込は「触ったとき」に起きるので、AI が触る前に設計判断をしてしまうことがあります。手順に「先に読め」と書いておけば、触る前に読みます。自動と指示の二重化です。

**補足: 自動と指示、どっちが先か。`CLAUDE.md` に書けば全部読まれるのか**

先に結論です。`CLAUDE.md` に「rules を読め」と書いても、ファイルは 1 つも自動では読まれません。`CLAUDE.md` は文章であって、書かれたパスを取り込む機能はありません。自動で読み込まれるものは、クライアントが決めた 3 つだけです。

| 時点 | 自動で読み込まれるもの | まだ読まれていないもの |
|---|---|---|
| セッション開始 | `CLAUDE.md` の全文。`paths` の無いルール。全スキルの説明文（名前と description だけ） | スキルの本文。`paths` 付きルール。仕様書。コード |
| スキルが選ばれた | そのスキルの `SKILL.md` 本文 | 仕様書。コード。`paths` 付きルール |
| AI が手順 1 に従い、ルールと仕様書を Read した | AI が明示的に読んだファイル（＝指示の経路） | 触っていない領域のルール |
| AI が `apps/backend/` のファイルを読む・編集する | `paths` が一致した `backend.md`（＝自動の経路。すでに読んでいれば重複しない） | `frontend.md`（まだ触っていない） |
| AI が `apps/frontend/` のファイルを触る | `frontend.md` | |

つまり時系列は次のどちらかです。

```text
手順に従った場合
  SKILL.md 本文 → 手順 1「ルールを読め」→ AI が backend.md を Read（指示）→ 仕様書 → 実装で apps/backend を触る（自動読込は既読なので何も起きない）

手順を飛ばした場合
  SKILL.md 本文 → 仕様書を読まずに apps/backend を編集し始める → その瞬間に backend.md が自動で付く（自動）→ AI が気づいて直す
```

理想は前者です。後者は「触ってから知る」ので、最初の編集がルール違反になっていることがあります。自動読込は保険であって、主経路は手順 1 の「先に読め」です。だからスキルの手順に書き、`CLAUDE.md` の作業順序にも書いています。

「全部読まれるわけではない」の意味も同じです。`CLAUDE.md` に `../sample-specs/` と書いてあっても、仕様書は AI が Read したときにだけ読まれます。読ませたいものは、パスを書くだけでなく「いつ読むか」を手順に書く必要があります。02 章の「目次だけ常駐、本文は貸出式」は、`CLAUDE.md` 自身にも当てはまります。

**疑問 2: フロントエンドのルールは要らないのか**

今回は要ります。ただし、それは「機能追加だから両方読む」という決まりがあるからではありません。

キャンセル機能は、画面仕様 SCR-010 に「キャンセルボタン」があり、API 契約に `POST /reservations/{id}/cancel` があります。つまり AI は `apps/frontend/`（ボタン）と `apps/backend/`（API）の両方を触ります。両方触るので、両方のルールが読み込まれます。

```text
apps/backend/src/.../Reservation.java を編集  → paths: apps/backend/** に一致 → backend.md が有効
apps/frontend/src/.../ReservationDetail.tsx を編集 → paths: apps/frontend/** に一致 → frontend.md が有効
```

もし依頼が「API だけ先に作って。画面は別の人がやる」なら、AI は `apps/frontend/` を触りません。触らなければ `frontend.md` は読み込まれません。これがパスで範囲を切る（path-scoped）ルールの意味です。使わない領域のルールでコンテキストを埋めないための仕組みです。

**疑問 3: そもそも AI はどうやって「フロントもバックも必要」と分かるのか**

ここは rules の話ではなく、AI が判断する場所です。材料は 3 つで、すべて事前に置かれています。

| 材料 | 何が分かるか |
|---|---|
| `CLAUDE.md` のリポジトリの地図 | 「Web 画面は `apps/frontend`、API は `apps/backend`」という対応 |
| 仕様書 | 画面仕様にボタンがある → 画面を触る。API 契約にエンドポイントがある → API を触る |
| 既存コード | どのファイルに何があるか。`Reservation` クラスの場所、予約詳細画面のファイル |

流れはこうです。

```text
「キャンセル機能を追加して」
  ↓ 仕様書を読む（手順 1 で「正本を読め」と書いてあるから）
画面仕様: SCR-010 にキャンセルボタン
API 契約: POST /reservations/{id}/cancel
  ↓ CLAUDE.md の地図で場所に変換
画面 → apps/frontend、API → apps/backend
  ↓ 両方のファイルを触る
  ↓ 触ったパスに一致する rules が自動で読み込まれる
backend.md と frontend.md
```

順番に注意してください。**rules を読んでから変更範囲を決めるのではなく、仕様書で変更範囲を決めてから、触るパスに応じて rules が付いてきます**。だから手順 1 で仕様書を読むことが一番重要で、ここを飛ばすと変更範囲を既存コードや推測から決めてしまいます。

**判断を間違えたら**

AI が「API だけでよい」と誤判断し、画面を触らなかった場合を考えます。この誤りは ③ では止まりませんが、後の層で拾われます。

- ⑤ テスト契約: 画面仕様 SCR-010 を根拠にした「ボタンからキャンセルできる」の行がないことに、人が気づける
- ⑩ レビュー: 仕様適合の観点に「要求を満たしているか」があり、画面仕様との照合で「ボタンが未実装」が指摘になる

01 章の「読むべきものを読まない」というズレは、手順 1 で止めます。それでも漏れたときのために、後ろの層があります。

### ④: 質問は仕様書で解決できないものだけ

BR-01〜03 で「誰が」「いつまで」は決まります。書いていない「繰り返し予約の扱い」だけが質問ファイルになります。06 章で見た通り、人は回答欄に 1 文字書くだけです。

「仕様を推測で埋める」というズレは、ここで止まります。

### ⑤: 完了条件が先に決まる

テストを先に書きます。「開始 30 分前ちょうど」「権限なし」「二重送信」など、境界値と異常系がこの時点で確定します。

「終わったと思い込む」というズレは、ここで止まります。完了条件が AI の外に、テストとして置かれたからです。

### ⑥: 編集のたびにフックが見ている

実装中、AI が `generated/` を触ろうとすれば拒否され、`git push --force` を打とうとすれば拒否されます。AI がルールを忘れていても止まります。

「既存コードを正解扱いして生成物を直す」「取り返しのつかない操作」は、ここで止まります。

### ⑦ と ⑧: 検証と自己チェック

対象テスト、lint、型チェックを実行し、結果を成功も失敗もそのまま報告します。画面があれば browser-test で「テストが通った」と「画面で動く」を分けて確認します。最後に「頼まれていないことをしていないか」を自己チェックします。

「品質を過信する」というズレは、ここで止まります。実行するコマンドが決まっていて、報告の形が決まっているからです。

### ⑨ から ⑪: 別の目で見る

PR には検証結果と未解決事項が書かれます。pr-review が動き、観点別のサブエージェントに差分と仕様だけを渡します。作者の意図は渡しません。挙がった指摘は裏取りしてから採用し、指摘ゼロの観点は「ゼロ」と明記します。CI が lint、テスト、ビルド、生成物の差分を機械的に見ます。

「小さなズレが積み重なる」は、ここで止まります。実装した AI とは別のコンテキストが、仕様と差分だけを見るからです。

### ⑫: 人が決める

残った指摘と残リスクを見て、人がマージを判断します。ゲートを例外的に外すなら、その責任も人が持ちます。

## なぜ「問題ない」と言えるのか

「AI がテストを書いて通ったから」ではありません。層が重なっているからです。

| 層 | 何を保証するか | 01 章のズレのどれを止めるか |
|---|---|---|
| 正本 | 何を作るべきかが AI の外に定義されている | 仕様を推測する |
| 読む順番（スキル） | 正本を読んでから判断する | 読むべきものを読まない |
| テスト契約 | 完了条件が実装前に固定されている | 終わったと思い込む |
| フック・権限 | 禁止操作が機械的に止まる | 既存コードを正解扱い、破壊的操作 |
| 品質ゲート | lint、テスト、ビルドを機械が判定する | 品質を過信する |
| 独立レビュー | 別コンテキストが仕様と差分だけを見る | 小さなズレの蓄積 |
| 人の承認 | 例外判断と最終責任 | すべての残余 |

どの層も単独では穴があります。注意書きは読み飛ばされ、フックは外せ、テストは書いた条件しか見ず、レビューは見落とします。重ねることで、1 つの穴がそのまま本番に届く確率を下げています。

## それでも残るもの

正直に書きます。次は上の層では止まりません。

- **仕様書そのものが間違っている**。AI は正本に忠実に作るので、正本が誤っていれば誤りを忠実に実装します。防ぐのは仕様書側のレビューです（本編 08 章）
- **テストに書かれていない業務ルール**。テスト契約に漏れた条件は検証されません。防ぐのは業務ルールに ID を付けてテストと対応させる運用です
- **フックのすり抜け**。フックはクライアント依存です。CI と権限で二重化します
- **レビューの見落とし**。AI も人も見落とします。だから「何を見て何を見ていないか」を報告に残します

失敗が起きたら `tasks/lessons.md` に書き、2 回目はルールかスキルかフックに昇格させます（07 章）。層は最初から完成しているのではなく、失敗のたびに厚くなります。

## 「問題ない」の正しい言い方

完了報告は「できました」ではなく、次の形になります。

```markdown
## 変更内容
- Reservation.cancel() と CancelReservationUseCase を追加

## 検証
- [x] ./gradlew :apps:backend:test （成功）
- [x] pnpm --filter frontend test / typecheck / build （成功）
- [x] SCR-010 でキャンセル操作を実ブラウザ確認
- [ ] 未実行: 負荷試験（対象外）

## レビュー
- 仕様適合: 指摘なし
- 既存機能への影響: 指摘 1 件（修正済み）
- テスト: 指摘なし
- セキュリティ: 対象外（認可ロジック変更なし）

## 未解決事項
- 繰り返し予約の全回キャンセルは別 issue

## 正本との差分
- Reservation.status に CANCELLED を追加。仕様書へ追記済み
```

「問題ない」とは「問題がゼロ」ではなく、「どこまで見て、何が残っているかを説明できる」状態のことです。それを AI に毎回言わせる仕組みが、この入門編で説明してきた全部です。

## 締め

AI に任せられる範囲は、AI の賢さで決まるのではありません。正本、テスト、フック、ゲート、レビューを設計した範囲に比例して広がります。設計した範囲の外は、今日も人がやります。だからエンジニアの仕事は消えず、この設計へ移動します。

明日からやる 1 つは 07 章に戻ってください。`CLAUDE.md` 1 枚と、レビューのスキル 1 枚です。
