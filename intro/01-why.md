# 01. なぜ「AI に読ませる仕組み」が必要か

この章で分かること:

- AI にコードを書かせるだけでは、なぜ仕様と違うものができるのか
- AI がズレる 5 つの型
- ズレを防ぐには「コードを書く前後」を設計する必要があること

## よくある失敗

チャットに「会議室予約にキャンセル機能を追加して」と書くと、AI は数分で動くコードを返してきます。
ところが、レビューすると次のようなことが起きます。

- 誰でもキャンセルできる実装になっている。業務では予約者本人と管理者だけのはずだった
- 開始 5 分前でもキャンセルできる。業務では 30 分前までと決まっていた
- 毎週繰り返す予約を 1 回分だけキャンセルする想定だったのに、全部消える
- API のエラー形式が、他の API と違う

コードは動きます。テストも通ります。しかし業務としては間違っています。

原因は AI の能力不足ではありません。AI は「業務ルールがどこに書いてあるか」「既存の API がどんな形か」を知らないまま、既存コードと一般常識から推測して埋めたのです。

## AI がズレる 5 つの型

| 型 | 何が起きるか | 防ぎ方 |
|---|---|---|
| 終わったと思い込む | 途中なのに「完了しました」と言う | 完了条件をチェックリストとして先に書いておく |
| 品質を過信する | テスト未実行、画面未確認でも良いと判断する | 実行すべき検証コマンドを明文化する |
| 小さなズレが積み重なる | 命名、責務、仕様の小差が積もって別物になる | 工程ごとに仕様書と実装を照合する |
| 読むべきものを読まない | 設計書や過去の判断を見ずに進める | 読む順番を手順書に書く |
| 既存コードを正解扱いする | 「今のコードがこうだから正しい」と判断する | 正本を決め、既存コードは参考情報にする |

この 5 つはすべて「AI の中で起きること」です。チャットで毎回注意しても、次のセッションでは忘れます。
だから、注意ではなくリポジトリのファイルとして外に出します。

## 外に出すもの

| AI の中にあると困るもの | ファイルにする | 置き場所 |
|---|---|---|
| どこから読み始めるか | 入口 | `CLAUDE.md` |
| この領域で常に守ること | ルール | `.claude/rules/` |
| この作業の進め方 | スキル | `.claude/skills/` |
| 何を作るべきか | 仕様書、業務ルール | 設計書リポジトリ |
| なぜそう決めたか | ADR | 設計書リポジトリ |
| 何ができれば完了か | テスト契約 | 作業フォルダ |
| 過去に何で失敗したか | 教訓ファイル | `tasks/lessons.md` |

この入門編で扱うのは、上の表を使って「コードを書く前」と「書いた後」に何をさせるか、です。

```text
依頼
  ↓ 書く前
入口で領域を分類 → ルールとスキルを読む → 仕様書を読む → 不明点だけ質問する
  ↓ 書く前
完了条件をテスト契約にする
  ↓
実装
  ↓ 書いた後
テスト・lint・ビルド → 自動レビュー → 仕様書との差分を報告
```

「書く前後」まで含めて設計している点が、単なるコード生成との違いです。

## AI 駆動開発が「そうではないもの」

- 生成されたコードをそのまま採用すること
- 人間が決めていない仕様を AI に推測させること
- テストを書かず、AI の「できました」を完了判定にすること
- レビューや権限や CI を、AI の注意力で置き換えること

AI は調査、比較、実装、検証、記録を高速にこなします。仕様の所有者と最終責任は人間のままです。
