# 08. 応用 1: AWS 読み取り連携

この章で分かること:

- 「ログ見て」の一言で AI が AWS を調査できる仕組み
- 安全を「お願い」ではなく IAM で保証する考え方
- 自分の環境に入れる手順と、スキルに書いてよいこと・いけないこと

## 何ができるようになるか

```text
「本番の API、さっきからエラー出てる？」
  ↓
AI が読み取り専用の権限で CloudWatch Logs を取得
  ↓
「直近 30 分で 5xx が 42 件。すべて /reservations/{id}/cancel。
  例外は NullPointerException で、開始時刻が null の予約が原因と推測される。
  観測事実と推測は分けて記載」
```

仕組みは 02 章とまったく同じです。説明文の「ログ見て」「エラー出てる？」が引き金になってスキルが選ばれ、本文の手順に従って AWS CLI を実行するだけです。新しい概念は 1 つもありません。

## 一番大事な点: 権限は IAM で絞る

スキルには「本番を壊さないこと」と書いても意味がありません。AI は忘れますし、指示は強制ではありません。

代わりに、AI が使うプロファイルに**読み取り専用の権限だけ**を付けます。

```bash
AWS_PROFILE=ai-readonly aws logs tail /app/backend --since 30m
```

`ai-readonly` に書き込み権限がなければ、AI がどんな判断をしても書き込みは失敗します。
「AI が壊さないこと」をプロンプトではなく IAM が保証する、というのがこの章の結論です。

ガードレールにはテスト、レビュー、権限の 3 つがあります。このうち権限だけが「物理的に」効きます。
だからスキルに書く手順は「守れ」ではなく「この範囲なら自由に動いてよい」という宣言になります。

## 入れる手順

### 1. IAM で読み取り専用の主体を作る

推奨はロールです。長期のアクセスキーを作らず、短期の資格情報を都度取得します。

- ポリシーは AWS 管理の `ReadOnlyAccess`、またはより狭い `ViewOnlyAccess`
- `ReadOnlyAccess` は S3 のオブジェクト取得などデータの読み取りも含みます。メタデータだけ見せたいなら `ViewOnlyAccess` を選びます
- 会社の SSO を使っているなら、SSO 側に読み取り専用のパーミッションセットを作る形でも同じです

### 2. ローカルにプロファイルを作る

`~/.aws/config` に AI 専用のプロファイルを足します。ロールを引き受ける例です。

```ini
[profile ai-readonly]
role_arn = arn:aws:iam::123456789012:role/ai-readonly
source_profile = default
region = ap-northeast-1
```

SSO の場合は次の形です。

```ini
[profile ai-readonly]
sso_session = my-org
sso_account_id = 123456789012
sso_role_name = ReadOnlyAccess
region = ap-northeast-1
```

動作確認は 1 行です。

```bash
aws sts get-caller-identity --profile ai-readonly
```

### 3. スキルを置く

`.claude/skills/aws-readonly/SKILL.md` を作ります。この repo のルートにある実物がそのまま使えます。要点だけ抜くと次の形です。

```markdown
---
name: aws-readonly
description: >
  AWS のリソース状態・ログ・メトリクスを調査する（読み取り専用）。
  「ログ見て」「デプロイ状態確認して」「ECS 落ちてない？」「エラー出てる？」で使う。
  リソースの作成・変更・削除には使わない。
---

# AWS 読み取り調査手順

## 前提
すべてのコマンドに `AWS_PROFILE=ai-readonly` を付ける。例外なし。

## 手順
1. 調査対象を特定する（サービス名、時間帯、症状）。
2. ログ → メトリクス → リソース状態の順で事実を集める。推測を挟まない。
3. 報告は「観測事実」と「そこからの推測」を分けて書く。
4. 書き込みが必要だと判断したら、実行せずコマンド案を提示して止まる。
```

### 4. 動かして確かめる

置いただけで成功と判断しません。次のように聞いて、意図した動きになるか確認します。

```text
- 「ECS のサービス一覧を見て」    → aws-readonly が選ばれ、ai-readonly で実行されるか
- 「このタスクを再起動して」      → 実行せず、コマンド案を提示して止まるか
- 「アクセスキーを表示して」      → 拒否するか
```

## スキルに書いてよいもの、いけないもの

| 書いてよい | 書いてはいけない |
|---|---|
| プロファイル名 | アクセスキー、シークレットキー |
| リージョン | MFA のシード |
| 認証を更新するスクリプトの場所 | パスワード |
| 秘密情報を安全に取得する手順 | DB 接続文字列に含まれる資格情報 |

スキルは秘密の値ではなく、秘密へ安全に到達する手順を持ちます。
リポジトリは公開されることもあります。値は OS のキーチェーンや Secrets Manager に置き、スキルには取り出し方だけを書きます。

## 安全原則

- 調査系（describe / get / list / logs）は自動で実行してよい
- 変更、削除、停止系は実行せず、人に確認する
- シークレットの値やアクセスキーは表示しない
- 出力は `--query` や `--output table` で絞る。ログを全部読ませるとコンテキストを浪費する
- プロファイルとリージョンは毎回明示する。既定プロファイル頼みにしない

## 発表での見せ方

見せるものはスキル 1 枚（20 行）と、ターミナル 1 画面です。

1. スキルの説明文を見せて「ログ見て、が引き金」と言う
2. 「直近 30 分のエラーログ見て」と打つ
3. `AWS_PROFILE=ai-readonly` が付いたコマンドが流れるのを見せる
4. 報告で「観測事実」と「推測」が分かれていることを指す
5. 「これで壊れないのは IAM のおかげで、プロンプトのおかげではない」で締める

事前に `aws sts get-caller-identity --profile ai-readonly` が通ることを確認しておきます。通らない場合はターミナルを使わず、スライドで手順だけ説明します。
