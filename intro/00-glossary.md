# 00. 用語集

先に全部覚える必要はありません。読んでいて分からない言葉が出たら、ここへ戻ってください。

## AI と道具

| 用語 | 意味 |
|---|---|
| AI エージェント | 依頼を受けて、ファイルを読み、コマンドを実行し、コードを書くところまで自律的に進める AI。チャットで答えを返すだけの AI と区別する |
| Claude Code | Anthropic 社の AI エージェント。ターミナルや IDE から使う。この入門編ではこれを前提にする |
| コンテキスト（context） | AI がいま判断に使える情報の総量。依頼文、会話履歴、読んだファイル、コマンドの結果。上限があるので、何を読ませるかが設計になる |
| サブエージェント（subagent） | 親の AI が仕事の一部を任せる、別のコンテキストを持つ AI。レビューの観点を分けるときなどに使う |

## リポジトリに置くファイル

| 用語 | 意味 |
|---|---|
| `CLAUDE.md` | AI が作業を始めるとき、毎回必ず読む入口ファイル。リポジトリの地図、作業順序、禁止事項、代表コマンドを短く書く |
| ルール（rule） | 対象領域で常に守る制約。`.claude/rules/` に領域ごとに置く。例: 「生成されたファイルは手で直さない」 |
| スキル（skill） | 特定の作業を進めるための手順書。`.claude/skills/<名前>/SKILL.md` に置く。例: 「PR をレビューする手順」 |
| 説明文（description） | スキルの先頭に書く「いつこのスキルを使うか」の短い文。AI はこれを見てスキルを選ぶ |
| フック（hook） | AI がファイルを編集した直後などに自動で走るスクリプト。「お願い」ではなく機械的に止めたいときに使う |

## 仕様と判断の記録

| 用語 | 意味 |
|---|---|
| 正本 | ある情報について「これが最終的な答え」と決めた文書。英語では SSoT（Single Source of Truth）。既存コードは正本ではない |
| 仕様書 | 何を作るかを書いた文書。画面仕様、API 仕様、データ定義など |
| 業務ルール | 業務上の決まり。例: 「会議開始 30 分前を過ぎたらキャンセルできない」。ID（例: BR-01）を付けて参照できるようにする |
| ADR | Architecture Decision Record。「なぜその設計を選んだか」を残す短い文書。仕様書が「今どうなっているか」を書くのに対し、ADR は「なぜそうしたか」を書く |
| 教訓ファイル（lessons） | 過去に AI や人が失敗した事例と再発防止策。AI が作業前に読む |

## 品質を守る仕組み

| 用語 | 意味 |
|---|---|
| ズレ（drift） | 仕様、設計、実装、テスト、文書の間に生まれる食い違い。AI 駆動開発で一番の敵 |
| テスト契約 | 実装前に「何が満たされれば完了か」をテストケースの形で固定した文書。AI が「できました」と自己判断するのを防ぐ |
| 品質ゲート（quality gate） | 次の工程へ進む前に必ず通す関所。lint、テスト、ビルド、レビューなど |
| 自動レビュー | AI に PR の差分をレビューさせること。観点を分けて別々のサブエージェントに見せると精度が上がる |
| 段階的読み込み（progressive disclosure） | 必要になった情報だけを順に読ませる設計。全部を最初に読ませない |

## 開発フロー

| 用語 | 意味 |
|---|---|
| AIDLC | AI Development Life Cycle。仕様書と規約があるプロジェクトで、AI のズレを抑えるための 5 フェーズの開発フロー。この入門編の主題 |
| フェーズ | AIDLC の工程。1 文脈の読み込み、2 方針のすり合わせ、3 テスト契約、4 テスト先行実装、5 検証と仕様書整合 |
| 質問ファイル | AI が人に判断を求めるとき、チャットではなくファイルとして書く質問。背景、根拠、選択肢、推奨を含む |
| 差分レポート | フェーズ 5 で作る「実装と仕様書のどこが食い違っているか」の一覧 |
