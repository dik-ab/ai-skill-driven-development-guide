# 03. 前提 2: 仕様書駆動の実装

この章で分かること:

- 「正本」を決めるとは何か
- 既存コードが正本ではない理由
- 仕様書が薄い組織で最初に整えるもの

## 正本を決める

正本とは「この情報について迷ったら、最終的にここを見る」と決めた文書です。
AI にとって正本がないと、既存コード、一般常識、依頼文のどれを信じればよいか判断できず、推測で埋めます。

情報の種類ごとに正本を決めます。会議室予約アプリなら次の形です。

| 情報 | 正本 | 置き場所の例 |
|---|---|---|
| 業務の決まり | 業務ルール（ID 付き） | `specs/business-rules.md` |
| API の形 | OpenAPI | `openapi.yaml` |
| 画面の見え方 | 画面仕様 | `specs/screens/SCR-010_reservation-detail.md` |
| データの形 | テーブル定義とマイグレーション | `specs/database.md`、`db/migrations/` |
| なぜそう決めたか | ADR | `specs/adr/` |

## 優先順位を決める

文書同士が矛盾したときの順番も決めます。

1. 業務ルール、契約仕様
2. アーキテクチャの設計書、ADR
3. 個別の仕様書（API、画面、DB）
4. コーディング規約
5. 既存コード
6. AI の推測

既存コードは 5 番目です。重要な参考情報ですが、正本ではありません。
既存コードと仕様書が食い違っていたら、AI は「矛盾がある」と報告し、どちらに合わせるかは人が決めます。

## 「質問する前に読む」

仕様書駆動のもう 1 つの柱は、AI が人に質問する前に必ず正本を読むことです。

```text
悪い流れ
  依頼 → 「キャンセルは誰ができますか？」とチャットで質問

良い流れ
  依頼 → 業務ルールを読む → BR-03「予約者本人と管理者」を見つける → 質問しない
  依頼 → 業務ルールを読む → 繰り返し予約の扱いが書いていない → ここだけ質問する
```

仕様書に答えがある質問を人に投げないこと。仕様書に答えがないものだけを、根拠付きで質問すること。
この 2 つを守るだけで、人とのやり取りは大幅に減ります。

## ADR は「なぜ」を残す

仕様書は「今どうなっているか」を書きます。ADR は「なぜそうしたか」を書きます。

コードを読めば「予約テーブルに `cancelled_at` 列がある」ことは分かります。
しかし「削除フラグではなく日時にした理由」「論理削除と物理削除を比較したか」は分かりません。
理由がないと、後から人も AI も一般論で過去の案へ戻してしまいます。

ADR は短くて構いません。「状況」「選択肢」「決定」「結果として受け入れること」の 4 項目があれば十分です。
すべての判断に書く必要はなく、後から戻すコストが高い判断だけに書きます。

## 仕様書が薄い組織はどうするか

最初から全部揃える必要はありません。優先順位はこの順です。

1. **業務ルールに ID を付ける**。1 行 1 ルールで、`BR-01` のように番号を振る。これだけで AI がテストと結び付けられる
2. **API 契約を機械可読にする**。OpenAPI があれば、AI は URL、リクエスト、レスポンスを推測しなくなる
3. **入口に正本の場所を書く**。`CLAUDE.md` に「仕様書はここ」と書く
4. 余裕が出たら画面仕様、テーブル定義、ADR を足す

仕様書がない領域は「ない」と明示します。AI が「仕様書に記載なし」と報告できれば、それ自体が仕様の穴の発見になります。

詳しくは本編の `../02-repository-and-docs-structure.md` と `../08-spec-repository-operation.md` を参照してください。
