# 06. 具体例: 会議室予約のキャンセル機能を 1 本通す

この章で分かること:

- 5 フェーズで実際に何が出力されるか
- 「仕様書に書いていないこと」がどう見つかり、どう処理されるか
- AI が勝手に埋めなかったことを、どこで確認するか

## 前提

架空の会議室予約アプリです。

```text
apps/web        Web 画面（React）
apps/api        API サーバー（Spring Boot）
openapi.yaml    API 契約
../specs/       仕様書（正本）
  business-rules.md
  screens/SCR-010_reservation-detail.md
  adr/
```

依頼は次の 1 行です。

```text
会議室予約にキャンセル機能を追加して
```

## フェーズ 1: 文脈の読み込み

AI が正本を読んで集めた事実です。

```text
読んだ文書
- specs/business-rules.md
- openapi.yaml
- specs/screens/SCR-010_reservation-detail.md
- apps/api/src/.../Reservation.java（既存コード）

関係する業務ルール
- BR-01: 予約は開始前だけキャンセルできる
- BR-02: 開始 30 分前を過ぎたらキャンセルできない
- BR-03: キャンセルできるのは予約者本人と管理者

関係する API と画面
- openapi.yaml に POST /reservations/{id}/cancel が定義済み。レスポンスは予約オブジェクト
- SCR-010 の予約詳細画面に「キャンセル」ボタンの記載あり

既存コード
- Reservation クラスに status 列があり、値は RESERVED / DONE のみ
- 通知を送る仕組みが既に存在する

仕様書に記述がない箇所
- 毎週繰り返す予約をキャンセルしたとき、1 回分か全回か
- キャンセル時に通知を送るか
```

ここでは「通知は送るべき」といった推奨は書きません。事実だけです。

## フェーズ 2: 方針のすり合わせ

AI はまず自己解決を試みます。

- 「誰がキャンセルできるか」は BR-03 に答えがある。質問しない
- 「期限」は BR-02 に答えがある。質問しない
- 「状態の値」は既存コードに CANCELLED がないが、追加は仕様書の範囲内。質問しない

残った 2 件だけを質問ファイルにします。

```markdown
## Q1. 繰り返し予約のキャンセルは 1 回分か全回か

### 背景
BR-01〜03 は単発予約を前提に書かれており、繰り返し予約に触れていない。
決めずに進めると、AI が推測で片方に寄せることになる。

### 正本上の根拠
- `specs/business-rules.md` BR-01〜03: 繰り返しへの言及なし
- `openapi.yaml` POST /reservations/{id}/cancel: id は 1 件の予約を指す

### 選択肢
| 観点 | A) 今回は 1 回分だけ | B) 全回をキャンセル | X) その他 |
|---|---|---|---|
| 正本との整合 | API の id が 1 件を指す形と一致 | API の変更が必要 | |
| 実装コスト | 小 | 中 | |
| 業務上の妥当性 | 「今週だけ休み」に対応できる | 「シリーズごと解約」に対応できる | |

### AI の推奨
A。現在の API 契約と整合し、B は別 issue で API を拡張してから対応できる。

### 回答欄
[Answer]:
```

人は `A` と書くだけです。回答後、確定方針ファイルに「繰り返し予約は 1 回分のみ。全回は別 issue」と残します。

## フェーズ 3: テスト契約

確定方針を、完了条件の表にします。

| ケース | 業務ルール | 前提 | 操作 | 期待 |
|---|---|---|---|---|
| 正常 | BR-01 | 開始 1 時間前、予約者本人 | cancel | 200、状態が CANCELLED |
| 期限ちょうど | BR-02 | 開始ちょうど 30 分前 | cancel | 200（30 分前「まで」は可） |
| 期限切れ | BR-02 | 開始 20 分前 | cancel | 409、状態は RESERVED のまま |
| 終了後 | BR-01 | 開始後 | cancel | 409 |
| 権限なし | BR-03 | 予約者でも管理者でもない | cancel | 403、保存処理が呼ばれない |
| 管理者 | BR-03 | 管理者 | cancel | 200 |
| 繰り返し | 決定 Q1 | 毎週予約の 1 回 | cancel | その回だけ CANCELLED、他の回は不変 |
| 二重送信 | 一般 | 同じリクエストを 2 回 | cancel | 2 回目も 200、通知は 1 回 |

「期限ちょうど」の行は、BR-02 の「30 分前を過ぎたら」が「以上」か「超」かを確認して書きます。
曖昧ならフェーズ 2 に戻して質問に加えます。

## フェーズ 4: テスト先行実装

実装を単位に分けます。

```text
U1 ドメイン層     Reservation.cancel(now, actor) を追加。BR-01〜03 の判定をここに置く
U2 アプリ層       CancelReservationUseCase。取得 → cancel → 保存 → 通知
U3 インフラ層     CANCELLED 状態の保存、マイグレーション
U4 API 層         POST /reservations/{id}/cancel の Controller、409/403 の変換
U5 Web 画面       SCR-010 にキャンセルボタンと確認ダイアログ
```

U1 から順に、テストを書いてから実装し、対象テストを実行します。
途中で「通知の仕様が書いていない」と再確認されますが、これはフェーズ 1 で挙げた未定義事項です。
確定方針に「通知は既存の仕組みで予約者へ送る」と決めてあれば進み、なければフェーズ 2 へ戻します。

## フェーズ 5: 検証と仕様書整合

実行した検証:

```text
./gradlew :apps:api:test        成功
pnpm --filter web test           成功
pnpm --filter web typecheck      成功
pnpm build                       成功
画面確認                         SCR-010 でボタン表示、確認ダイアログ、キャンセル後の表示を確認
```

実装と仕様書の差分:

| 分類 | 内容 | 対応 |
|---|---|---|
| マージ前に文書更新 | `Reservation.status` に CANCELLED を追加した。仕様書のデータ定義に値がない | 仕様書へ追記 |
| マージ前に文書更新 | 繰り返し予約は 1 回分のみという決定 | 業務ルールに BR-04 として追記 |
| 別 issue | 全回キャンセルの API | issue を作成 |
| なし | 実装にだけ存在するフィールド | 追加していないことを確認済み |

最後の行が重要です。AI が「キャンセル理由」のような便利そうなフィールドを勝手に足していないことを、ここで確認します。

## この例で AI が「しなかった」こと

- 業務ルールに答えがある質問を人に投げなかった
- 繰り返し予約の扱いを推測で決めなかった
- 仕様書にないフィールドを足さなかった
- テスト未実行のまま「完了」と言わなかった
- 仕様書との差分を隠さなかった

これらは AI の性格ではなく、`aidlc` スキルと `CLAUDE.md` の「仕様通りに作れないときは止まって聞く」が毎回そうさせています。
